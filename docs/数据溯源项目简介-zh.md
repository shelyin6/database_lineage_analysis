## 一、项目一句话介绍

SQL 元数据查看器是一套不依赖业务数据库、直接读取本地 SQL 文件的可视化分析系统，用于统一查看表结构、存储过程、表与过程之间的数据流关系，并对字段级直接取值关系进行溯源定位，帮助开发、运维、数据治理和业务分析人员快速回答“这张表是什么、由谁加工、依赖什么、字段从哪里来、修改后会影响什么”等问题。

## 三、项目背景

### 3.1 现实场景

在数据仓库、数据集市、监管报送、核心业务数据加工和指标平台中，通常会存在大量：

- 表结构 SQL 文件
- 存储过程 SQL 文件
- 初始化脚本
- 增量加工脚本
- 临时表和中间表脚本
- 备份过程或历史版本过程
- 不同模式或不同业务域的 SQL 文件

当系统规模达到数百张表、数百个存储过程后，单纯依赖文件目录和文本搜索，会逐渐出现明显问题。

### 3.2 当前典型规模

本项目针对的典型场景是：

- 约 800 张表
- 约 400 个存储过程
- 表之间不直接完成完整的数据加工
- 主要通过存储过程完成数据清洗、转换、汇总和装载
- 存在 ALMP、IDS、FDS 等多个模式或数据域
- 表名、存储过程名具有一定命名规范
- SQL 文件可能来自多个目录、多个版本或多个交付批次

当前仓库样例 SQL 的一次解析抽样结果约为：

- 858 张表
- 269 个存储过程

实际运行结果以当前目录下 SQL 文件内容为准，新增或删除 SQL 文件、表和过程后，重新加载会重新计算结果。

### 3.3 传统分析方式的问题

#### 问题一：找表容易，找加工关系困难

通过文件搜索可以找到表名，但很难快速回答：

- 谁写入了这张表？
- 谁读取了这张表？
- 这张表是中间表、结果表还是基础表？
- 这张表有没有真正参与数据流转？

#### 问题二：存储过程数量多，人工阅读成本高

一个存储过程可能包含：

- 多个目标表
- 多个来源表
- 多层嵌套查询
- 临时表
- CTE
- 动态 SQL
- 删除、插入、更新、合并等多种操作

人工逐个打开 SQL 文件、定位关键语句、整理依赖关系，效率低且容易遗漏。

#### 问题三：表与过程之间缺少统一入口

传统文件阅读通常以 SQL 文件为入口：

```text
先打开文件
    -> 搜索过程名称
        -> 搜索目标表
            -> 再搜索 FROM/JOIN 来源表
                -> 再定位字段
```

本项目把入口调整为：

```text
选择表
    -> 查看数据来源过程
        -> 查看来源表
            -> 查看字段直接来源
                -> 点击溯源定位到存储过程代码行
```

#### 问题四：字段级关系最难确认

表级关系只能说明“某过程使用了某张表”，但无法直接说明：

- 目标表的 `ACCT_NUM` 来自哪个来源表字段？
- 目标表的 `GK_PRODUCT_NUM` 来自哪个来源字段？
- 哪些字段是直接取值？
- 哪些字段经过了 CASE、函数、聚合或多层计算？

#### 问题五：数据库不可访问或不适合直接连接

在以下场景中，直接连接数据库不一定可行：

- 内网隔离环境
- 开发机没有数据库权限
- 生产环境不允许查询元数据
- SQL 文件已经交付，但数据库暂时不可用
- 需要对历史版本 SQL 进行离线分析
- 需要在不影响生产库的情况下进行依赖梳理

## 四、项目建设目标

### 4.1 总体目标

建立一个轻量、离线、可部署、可追溯的 SQL 元数据分析工具，把分散的 SQL 文件转化为统一的对象目录、关系索引和字段溯源结果。

### 4.2 具体目标

1. 自动识别 SQL 文件中的表和存储过程。
2. 解析表结构、字段类型、注释、默认值和源码位置。
3. 解析存储过程参数、注释、目标表和来源表。
4. 建立表与存储过程之间的双向关系索引。
5. 支持表级数据来源和引用关系查询。
6. 对直接字段取值建立字段级来源关系。
7. 对无法确认的复杂计算字段保持为空，避免误报。
8. 点击来源表时可以跳转到对应表和字段。
9. 点击溯源时可以跳转到存储过程指定代码行。
10. 支持 SQL 文件变更后的重新解析。
11. 支持在内网通过一个胖 Jar 包直接运行。
12. 支持本地保存表备注、字段码值和业务属性。

### 4.3 非目标

当前系统不是以下系统：

- 不是数据库管理工具
- 不是 SQL 执行平台
- 不是数据查询平台
- 不是调度平台
- 不是实时血缘采集平台
- 不是业务数据质量检测平台
- 不是自动生成生产批次的调度编排系统

系统当前重点是：**基于 SQL 文本做静态元数据和数据流关系分析**。

## 五、项目整体方案

### 5.1 总体思路

系统采用“文件扫描 + SQL 静态解析 + 内存索引 + 前端可视化”的方式运行。

```text
SQL 文件
    |
    v
文件扫描与分类
    |
    v
表结构解析 ----------------------+
    |                             |
    v                             v
TableMetadata              存储过程解析
                                  |
                                  v
                           ProcedureMetadata
                                  |
             +--------------------+--------------------+
             |                    |                    |
             v                    v                    v
       表级关系索引        过程调用关系索引       字段直接溯源解析
             |                    |                    |
             +--------------------+--------------------+
                                  |
                                  v
                         MetadataSnapshot
                                  |
                                  v
                            REST API
                                  |
                                  v
                         Vue 可视化页面
```

### 5.2 方案特点

#### 离线

不依赖业务数据库，不需要数据库账号，不执行 SQL，不改变业务系统状态。

#### 轻量

后端是 Spring Boot 单体应用，前端使用打包在项目中的 Vue 运行时，部署为一个可执行胖 Jar。

#### 可追溯

每个解析对象都保留来源文件、起始行号、结束行号和原始 SQL。

#### 可扩展

表解析、存储过程解析、字段溯源和前端展示相互独立，后续可以继续增加：

- 更多 SQL 方言
- 更多 DML 类型
- 批次依赖分析
- 图形化 DAG
- SQL 差异对比
- 影响分析

## 八、SQL 解析能力

### 8.1 表结构解析

系统能够识别常见表结构定义，例如：

```sql
CREATE TABLE ALMP.DM_O_CORP_CUST (
    DATA_DT DATE NOT NULL COMMENT '数据日期',
    CUST_NUM VARCHAR(64) COMMENT '客户编号',
    CUST_NAME VARCHAR(200) COMMENT '客户名称'
);
```

解析结果包括：

- 表名和 schema
- 表级注释
- 字段顺序
- 字段类型
- 类型参数
- `NOT NULL`
- `DEFAULT`
- 字段 `COMMENT`
- 建表 SQL 所在行号

### 8.2 存储过程识别

系统识别：

```sql
CREATE OR REPLACE PROCEDURE ALMP.PROC_DM_O_CORP_CUST(...)
```

并按存储过程边界截取过程原文，保留：

- 过程定义头
- 参数区域
- 注释说明
- 过程正文
- 异常处理
- 结束位置

### 8.3 目标表识别

当前表级解析可以识别以下类型的目标表操作：

- `INSERT INTO`
- `INSERT OVERWRITE INTO`
- `MERGE INTO`
- `UPDATE`
- `TRUNCATE TABLE`
- `DELETE FROM`
- `ALTER TABLE`

目标表关系用于回答：

> 哪些存储过程会写入或加工这张表？

### 8.4 来源表识别

当前表级解析可以识别：

- `FROM`
- `JOIN`
- `USING`
- CTE 中的来源表
- 部分动态 SQL 字符串中的来源表

来源表关系用于回答：

> 这个存储过程读取了哪些表？

### 8.5 CTE 处理

对于以下结构，系统会尝试识别 CTE 名称并排除 CTE 名称对真实物理表的干扰：

```sql
WITH TMP_BASE AS (
    SELECT *
    FROM ALMP.DM_S_BASE
),
TMP_LABEL AS (
    SELECT *
    FROM ALMP.DM_S_LABEL
)
SELECT *
FROM TMP_BASE B
LEFT JOIN TMP_LABEL L
    ON B.ID = L.ID;
```

表级关系会重点保留：

- `ALMP.DM_S_BASE`
- `ALMP.DM_S_LABEL`

而不是把 `TMP_BASE` 和 `TMP_LABEL` 当成真实物理表。

### 8.6 动态 SQL 处理

如果存储过程中存在字符串形式的 SQL，例如：

```sql
V_SQL := 'INSERT INTO ALMP.DM_O_TARGET SELECT * FROM ALMP.DM_S_SOURCE';
EXECUTE IMMEDIATE V_SQL;
```

系统会尝试从 SQL 字符串中提取表级目标和来源关系。

需要注意：

- 动态 SQL 的字段级溯源当前不保证完整。
- 复杂字符串拼接可能无法还原为完整 SQL。
- 动态表名、动态字段名和变量替换会降低静态分析准确率。

### 8.7 注释与字符串处理

解析器在识别关键字时会处理：

- 单行注释
- 块注释
- 单引号字符串
- 双引号标识符
- 括号嵌套

这样可以减少以下误识别：

- 注释里的 `FROM`
- 字符串里的 `JOIN`
- 嵌套子查询里的错误边界
- 字符串常量中的括号

## 九、字段级直接溯源

### 9.1 功能定义

字段级溯源用于展示：

```text
目标表字段 <- 来源表字段
```

例如：

```text
ALMP.DM_O_DEP_DD_ACCT.ACCT_NUM
    <- ALMP.DM_S_DEP_ACCT_AVG.ACCT_NUM
```

### 9.2 当前识别原则

只有当 SELECT 投影项可以明确判断为一个直接字段引用时，系统才会生成来源关系。

可以识别：

```sql
B.ACCT_NUM
A.CUST_NUM
T1.GK_PRODUCT_NUM
ALMP.DM_S_SOURCE.FIELD_A
```

也可以处理：

- 表别名
- schema.表名.字段
- 嵌套子查询中的直接字段输出
- 部分 CTE 直接字段输出

### 9.3 主动置空的复杂表达式

以下表达式不会被错误地当成直接来源：

```sql
CASE WHEN A.FLAG = '1' THEN B.AMOUNT ELSE 0 END
```

```sql
NVL(B.CUR_BAL, 0)
```

```sql
SUM(B.AMOUNT)
```

```sql
B.AMOUNT * C.RATE
```

```sql
A.NAME || B.NAME
```

```sql
SUBSTR(A.CUST_NUM, 1, 6)
```

```sql
I_DATADATE
```

这类字段在页面中显示为空或使用占位符，表示：

> 当前规则无法将它判定为“单一直接来源字段”。

### 9.4 为什么复杂字段置空

字段来源分析最重要的是可信度。

如果一个字段是：

```sql
CASE WHEN ... THEN A.VALUE ELSE B.VALUE END
```

强行显示为 `A.VALUE` 会造成误导，因为实际来源可能是 A 或 B。

如果一个字段是：

```sql
SUM(A.VALUE)
```

它的来源不再是简单的一对一字段复制，而是聚合后的派生值。

因此系统采用保守策略：

```text
能明确确认 -> 展示来源
无法明确确认 -> 留空
```

### 9.5 字段溯源示例

目标表字段列表：

| 目标字段 | SELECT 表达式 | 结果 |
|---|---|---|
| `ACCT_NUM` | `B.ACCT_NUM` | `DM_S_DEP_ACCT_AVG.ACCT_NUM` |
| `CUST_NUM` | `A.CUST_NUM` | `DM_S_DEP_DD_ACCT.CUST_NUM` |
| `GK_PRODUCT_NUM` | `T1.GK_PRODUCT_NUM` | `DM_S_DEP_ACCT_LABEL.GK_PRODUCT_NUM` |
| `DATA_DT` | `I_DATADATE` | 空 |
| `CORP_ID` | `'810'` | 空 |
| `CUR_BAL` | `CASE WHEN ... END` | 空 |

## 十、表与存储过程关系

### 10.1 数据来源过程

页面中的“数据来源过程”表示：

> 将当前表作为目标表写入、装载或加工的存储过程。

从表详情进入后，可以看到：

- 过程名称
- 过程文件
- 过程行号范围
- 该过程的来源表
- 来源表是否为临时表
- 点击过程跳转
- 点击来源表跳转

### 10.2 引用本表的存储过程

页面中的“引用本表的存储过程”表示：

> 在来源关系中读取、引用或使用当前表的存储过程。

从表详情进入后，可以看到：

- 引用当前表的过程
- 每个过程的目标表
- 目标表是否为临时表
- 点击目标表跳转
- 点击过程跳转

### 10.3 为什么两个关系可能出现相同过程

同一个存储过程可能同时：

- 读取当前表
- 又写入当前表

例如：

```sql
INSERT INTO ALMP.DM_O_TARGET
SELECT ...
FROM ALMP.DM_O_TARGET;
```

或者过程先读取历史分区，再回写同一张表。

因此：

- 出现在“数据来源过程”中，表示它把当前表作为目标加工。
- 出现在“引用本表的存储过程”中，表示它把当前表作为来源读取。

两个关系从不同方向描述同一个过程，不是重复统计错误。

### 10.4 忽略不产生数据的过程

当前系统会忽略：

```text
ALMP.PROC_ALMP_ADD_PARTITION
```

原因是该过程主要用于分区操作，不应被当成实际的数据加工过程。

这可以避免：

- 误把分区维护过程算作数据来源过程
- 误把分区维护过程算作数据依赖
- 影响孤表判断
- 污染数据流关系

## 十三、数据流分析流程

### 13.1 启动加载流程

```text
应用启动
    |
    v
定位应用目录
    |
    v
读取外部 application.yml
    |
    v
确定 SQL 目录
    |
    v
扫描 .sql 文件
    |
    +--> 识别表结构文件
    |
    +--> 识别存储过程文件
    |
    v
解析 TableMetadata
    |
    v
解析 ProcedureMetadata
    |
    v
关联过程调用关系
    |
    v
构建表级关系索引
    |
    v
构建字段级直接溯源索引
    |
    v
生成 MetadataSnapshot
    |
    v
提供 REST API
```

### 13.2 表级关系构建

对于每个存储过程，系统会得到：

```text
目标表集合
来源表集合
被引用表集合
调用过程集合
```

再构建三类主要索引：

```text
proceduresByReferencedTable
proceduresByTargetTable
proceduresBySourceTable
```

### 13.3 字段级关系构建

对于每个过程中的：

```sql
INSERT INTO target_table (target_col_1, target_col_2, ...)
SELECT source_expr_1, source_expr_2, ...
FROM source_table;
```

系统按照目标字段与 SELECT 表达式的序号进行对应：

```text
target_col_1 <- source_expr_1
target_col_2 <- source_expr_2
```

如果 `source_expr_n` 是直接字段引用，就生成 `ColumnLineage`；否则不生成。

### 13.4 目标字段列表与 SELECT 列表

优先使用 INSERT 中显式声明的目标字段列表：

```sql
INSERT INTO TARGET_TABLE (
    COL_A,
    COL_B
)
SELECT
    A.COL_X,
    B.COL_Y
FROM ...
```

当 INSERT 未显式声明目标字段时，系统尝试使用已解析表结构中的字段顺序进行对应。

### 13.5 索引优势

页面访问表详情时，不需要重新扫描全部 SQL 文件，而是直接从内存快照查询：

```text
表名
    -> 目标过程索引
    -> 来源过程索引
    -> 字段溯源索引
```

这样可以让页面交互保持简单、稳定和可预测。

## 十四、典型业务场景

### 14.1 场景一：空表恢复与重跑分析

问题：

> 目标表没有数据，需要分析哪些存储过程需要重跑，以及依赖哪些表。

使用方式：

1. 搜索目标表。
2. 打开“来源与引用”。
3. 查看“数据来源过程”。
4. 展开每个过程的来源表。
5. 继续进入来源表查看上游来源过程。
6. 逐层向上追溯到已有数据的基础表。
7. 根据过程依赖关系整理批次和重跑顺序。

系统能够提供：

- 目标表的直接加工过程
- 过程的来源表
- 来源表的上游过程
- 表是否为孤表
- 临时表和中间表提示

系统不会自动决定生产调度顺序，但可以显著减少整理依赖链的人工工作。

### 14.2 场景二：字段口径追溯

问题：

> 结果表字段的值到底来自哪个上游字段？

使用方式：

1. 打开目标表字段信息。
2. 找到目标字段。
3. 查看“直接来源”。
4. 点击来源字段查看来源表字段。
5. 点击“溯源”进入存储过程对应代码行。

适合：

- 指标口径核对
- 字段变更评估
- 数据质量排查
- 业务解释
- 监管字段追溯

### 14.3 场景三：表结构变更影响分析

问题：

> 修改一个字段名称、类型或含义，会影响哪些过程和目标表？

使用方式：

1. 搜索目标表。
2. 查看“引用本表的存储过程”。
3. 查看这些过程的目标表。
4. 点击过程查看原始 SQL。
5. 使用字段筛选或浏览代码定位字段使用位置。

可以辅助判断：

- 哪些存储过程直接读取该表
- 哪些结果表可能受到影响
- 是否存在临时加工链路
- 是否存在孤立或未识别关系

### 14.4 场景四：新人快速熟悉数据模型

问题：

> 新成员面对数百张表和数百个过程，无法快速建立整体认知。

使用方式：

1. 按 schema 和命名分组浏览。
2. 先从 DM_O 结果表开始。
3. 查看数据来源过程。
4. 逐级跳转来源表。
5. 对关键字段执行溯源。

系统提供：

- 统一入口
- 分组目录
- 表和过程双向导航
- 代码行定位
- 字段级来源展示

### 14.5 场景五：SQL 版本交付检查

问题：

> 交付了一批新的 SQL 文件，需要快速了解新增和删除了什么。

使用方式：

1. 替换 SQL 文件。
2. 重启应用或点击重新解析。
3. 查看对象数量和列表变化。
4. 搜索新增表和新增过程。
5. 查看目标表和来源表关系。
6. 检查新过程是否存在孤表或缺失来源。

## 十七、PPT 演讲稿素材

### 17.1 30 秒版本

> SQL 元数据查看器是一套面向本地 SQL 文件的静态分析工具。它不连接业务数据库，直接解析表结构和存储过程，自动建立表与过程之间的数据流关系，并进一步识别字段的直接来源。使用人员可以从一张目标表找到加工它的存储过程、来源表和字段来源，也可以点击溯源直接跳转到存储过程对应代码行。系统通过一个胖 Jar 包即可在内网部署，适合数据仓库开发、运维、交付和数据治理场景。

### 17.2 2 分钟版本

> 在大规模数据仓库中，表和存储过程往往分散在数百个 SQL 文件中。传统方式只能依赖文本搜索，无法快速建立完整的数据流关系，更难回答一个字段究竟来自哪个上游字段。  
>   
> SQL 元数据查看器的做法是直接扫描本地 SQL 文件，解析表结构、字段定义、存储过程参数、目标表和来源表，然后在内存中建立关系索引。页面提供表和存储过程两类目录，并按照 schema、数据层级和临时表进行分组。  
>   
> 在表详情中，用户可以看到数据来源过程、引用本表的过程、来源表和目标表。字段信息中，系统只展示可以明确判断的直接字段来源，复杂计算字段主动置空，避免产生误导。点击来源字段可以跳转到对应表字段，点击溯源可以直接定位到存储过程指定代码行。  
>   
> 系统使用 Spring Boot 和 Vue 3，前端资源内置，不依赖公网，最终打成一个胖 Jar，适合内网离线使用。

### 17.3 5 分钟版本

> 项目主要解决三个层面的问题。第一，解决 SQL 文件资产分散的问题，把表结构和存储过程统一成可搜索的元数据目录。第二，解决表级依赖难整理的问题，通过目标表、来源表和过程调用建立双向关系。第三，解决字段口径难追溯的问题，对直接取值字段进行字段级来源分析，并提供代码行定位。  
>   
> 系统启动时会扫描配置目录中的 SQL 文件，识别表结构和存储过程。表解析结果包括表名、schema、字段、类型、注释、默认值和源文件行号。过程解析结果包括参数、注释、目标表、来源表、被引用表、调用过程和原始 SQL。解析完成后，系统构建内存快照，并通过 REST 接口提供给前端。  
>   
> 页面左侧提供表和过程分组目录。分组按照 ALMP、IDS 等 schema 以及 DM_I、DM_A、DM_S、DM_O 和临时表进行组织，分组默认收起，适合数百个对象的浏览。右侧详情分为基本信息、来源与引用、字段信息和原始 SQL。左右两侧独立滚动，适合同时浏览长列表和长 SQL。  
>   
> 字段溯源是系统的一个重要能力。对于 `A.FIELD`、`B.FIELD` 这种可以明确判断的直接取值，系统展示来源表字段。对于 CASE、函数、聚合、算术等复杂表达式，系统不强行猜测，而是主动留空。点击溯源后，系统会打开对应存储过程、清理筛选条件、显示绝对行号并高亮目标代码行。  
>   
> 项目还支持表备注、表中文名、日期字段、增全量标记、表类型、表状态和字段码值维护，这些信息单独保存到 SQLite，不会被 SQL 文件重新解析覆盖。整个系统可以打成胖 Jar 放到内网，Jar 同级放 SQL 文件即可启动。

## 二十三、性能和可维护性设计

### 23.1 内存快照

系统启动或重新解析后，将结果封装到 `MetadataSnapshot` 中：

- 表列表
- 过程列表
- 文件摘要
- 表到过程索引
- 字段溯源索引

页面查询主要基于内存数据，不需要每次重新读取 SQL 文件。

### 23.2 前端缓存

前端缓存：

- 表列表
- 过程列表
- 表详情
- 过程详情

这样可以减少重复请求，提升对象之间连续跳转的速度。

### 23.3 局部刷新

点击重新解析时：

1. 后端重新扫描 SQL 文件。
2. 前端清理对象缓存。
3. 重新加载当前列表和详情。

### 23.4 跳转状态保留

页面历史状态中会保存：

- 当前 Tab
- 搜索条件
- schema
- 关系筛选
- 表类型
- 表状态
- 当前对象
- 过程聚焦行号

### 23.5 结果可信度优先

字段溯源没有采用“尽可能猜测”的策略，而是采用：

```text
规则明确 -> 生成关系
规则不明确 -> 不生成关系
```

这样更适合用于数据治理和影响分析的辅助判断。

## 二十四、当前能力边界

### 24.1 字段级溯源主要面向 INSERT SELECT

当前字段级直接来源重点支持：

```sql
INSERT INTO ... SELECT ...
```

对于以下场景仍可能需要增强：

- `UPDATE ... SET`
- `MERGE ... WHEN MATCHED`
- 多层动态 SQL
- PL/SQL 变量间接赋值
- 复杂函数展开
- 多分支条件来源
- 聚合字段来源明细
- 窗口函数来源
- 递归 CTE

### 24.2 复杂表达式只显示为空

当前系统不展开：

- 函数内部字段依赖
- CASE 分支集合
- 聚合前完整来源集合
- 算术运算依赖
- 多字段拼接依赖

这不是解析失败，而是当前产品策略：

> 第一阶段先保证直接关系准确，复杂关系留待后续增强。

### 24.3 静态分析无法等价运行时分析

SQL 文本解析无法完全获得：

- 运行时动态表名
- 参数实际值
- 条件实际走向
- 数据质量
- 真实执行顺序
- 调度系统依赖
- 数据量和耗时

因此系统结果应作为：

```text
SQL 级静态分析结果
```

而不是：

```text
生产运行时完整事实
```

### 24.4 表命名规范影响分组质量

当前分组依赖名称规则：

- `DM_I`
- `DM_A`
- `DM_S`
- `DM_O`
- `PROC_`
- `MID`
- `TMP`
- `TEMP`

如果新项目命名规则完全不同，分组需要配置化。

## 二十八、答辩和评审常见问题

### 问题一：系统是否连接数据库？

回答：

> 当前系统不连接业务数据库，只读取本地 SQL 文件，属于静态 SQL 元数据分析工具。用户不需要提供业务数据库账号，也不会读取业务表数据。

### 问题二：SQL 文件变更后是否需要重新导入？

回答：

> 不需要单独导入。重启应用或点击页面的重新解析按钮，系统会重新扫描 SQL 文件并重建元数据快照。

### 问题三：字段来源是否能够覆盖所有计算场景？

回答：

> 当前优先支持可以明确判断的直接取值字段。对于 CASE、函数、聚合、算术和多层计算，系统主动置空，避免错误归因。后续可以继续扩展复杂表达式解析。

### 问题四：同一个过程为什么可能同时出现在两个关系模块？

回答：

> 两个模块代表不同方向。如果过程读取当前表，它会出现在“引用本表的存储过程”；如果过程写入当前表，它会出现在“数据来源过程”。同一过程既读又写时，可能同时出现，这是正常的。

### 问题五：系统能否自动生成重跑顺序？

回答：

> 当前版本提供表和过程依赖关系，能够辅助人工整理重跑链路。完整的批次拓扑排序、并发批次和调度建议属于后续增强方向。

### 问题六：孤表是什么意思？

回答：

> 当前系统中，孤表是没有被识别到目标过程或来源过程关系的表。它可能是未接入的基础表、历史表、配置表、脚本未覆盖的表，也可能是解析规则尚未识别的特殊 SQL，需要结合实际业务进一步判断。

### 问题七：为什么选择胖 Jar？

回答：

> 胖 Jar 把应用和依赖一起打包，内网部署时只需要准备 Java 环境、Jar 和 SQL 文件，不需要安装独立 Web 服务器，也不需要访问公网下载前端依赖。

### 问题八：用户备注会不会在重新解析时丢失？

回答：

> 不会。SQL 解析结果保存在内存快照，用户维护的表备注和码值保存在独立 SQLite 文件中，重新解析不会删除这些内容。

## 二十九、项目亮点总结

### 亮点一：不依赖业务数据库

适用于内网、离线、权限受限和 SQL 交付场景。

### 亮点二：表、过程、字段三层关联

不是只展示表结构，而是进一步展示：

```text
表
  -> 存储过程
      -> 来源表
          -> 来源字段
              -> 源代码行
```

### 亮点三：双向导航

既能从表找到过程，也能从过程找到表；既能从目标字段找到来源字段，也能从来源字段回到加工代码。

### 亮点四：保守溯源

对复杂计算保持空白，优先保证结果可信。

### 亮点五：适配大规模对象目录

通过 schema、数据层级、临时表和分组折叠，降低数百对象的浏览成本。

### 亮点六：可直接部署

一个胖 Jar 加 SQL 文件即可运行。

### 亮点七：解析结果和业务维护分离

SQL 元数据动态重建，业务备注和码值独立持久化。

## 三十、最终项目总结

SQL 元数据查看器把原本分散在 SQL 文件、过程代码和人工笔记中的信息，统一沉淀为可搜索、可浏览、可跳转和可追溯的元数据视图。

它的核心价值不只是“把 SQL 展示出来”，而是完成了以下转换：

```text
分散的 SQL 文件
    -> 统一对象目录
    -> 表结构元数据
    -> 存储过程元数据
    -> 表级数据流关系
    -> 字段级直接来源
    -> 存储过程代码行定位
```

对于大规模数据仓库场景，它可以作为：

- SQL 资产浏览工具
- 表和过程依赖分析工具
- 字段口径辅助核对工具
- 空表恢复和重跑分析辅助工具
- 影响分析辅助工具
- 数据治理元数据底座
- 内网 SQL 交付检查工具

最终目标是让数据开发、数据运维、数据治理和业务分析人员，不再依赖大量人工文件搜索，而是通过统一界面快速理解数据加工链路。
